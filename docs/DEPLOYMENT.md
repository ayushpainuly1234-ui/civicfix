# Deployment Guide

CivicFix is a single-origin Express app: the same Node.js service serves the frontend in `public/` and the REST API. It needs **both PostgreSQL and MongoDB**; deployment will fail until both connection strings are configured.

## 1. Prepare the databases

### PostgreSQL (Neon)

1. Create a Neon project and database.
2. Copy its PostgreSQL connection string, preferably the pooled connection string for an app service.
3. If a database password has been shared or exposed, reset it and use the newly generated string.
4. Keep the connection string private. Do not commit it or paste it into issue trackers.

### MongoDB (Atlas)

1. Create a cluster and a database user with a strong unique password.
2. Copy the connection string for that database user and replace the database/placeholder parts with the `civicfix` database as appropriate.
3. Configure Atlas network access to permit the deployed service to connect. Prefer the narrowest supported access configuration; do not publish database credentials.
4. Keep `MONGO_URI` private.

## 2. Deploy from Render Blueprint

The root `render.yaml` configures a Node web service with health check `/api/health`, generated `JWT_SECRET`, automatic deploys after configured CI checks, and a one-time initial seed hook.

1. Open the [Render Dashboard](https://dashboard.render.com/).
2. Choose **New → Blueprint** and connect `ayushpainuly1234-ui/civicfix`.
3. Review the detected service. Do not change the repo or branch; the service uses `main`.
4. When prompted for unsynced environment variables, supply the secret values below.
5. Apply the Blueprint, then monitor the build, deploy and initial seed-hook logs.

## 3. Required environment variables

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `JWT_SECRET` | Random secret; Blueprint generates this automatically |
| `MONGO_URI` | Private MongoDB Atlas connection string |
| `MONGO_DB` | `civicfix` |
| `DATABASE_URL` | Private Neon PostgreSQL connection string |
| `ADMIN_EMAIL` | The email for the initial admin account |
| `ADMIN_PASSWORD` | Unique strong password, not the public demo password |
| `TRUST_PROXY` | `1` for Render's proxy |

Do not use the local demo admin password in production. The server configuration intentionally refuses to start in production if the admin password is missing or still matches the demo credential. Do not share secrets in chat or commit them to GitHub.

## 4. Check the deployment

After Render reports the deploy as live:

1. Open `https://YOUR-SERVICE.onrender.com/api/health`. It should return a JSON response with `status: "ok"`.
2. Open the service root URL and confirm the frontend renders.
3. Test citizen registration, sign-in, report creation and sign-out. All state-changing API calls must include the same-origin request header; the shipped browser client adds it automatically.
4. Check that the seed completed successfully. It creates the PostgreSQL schema, road graph, demo crews/admin and fictional example reports.
5. Test admin-only road closure and repair planning in a separate browser/session.
6. Set the GitHub repository's **About → Website** field to the final Render URL only after the app has passed the checks above.

## 5. Troubleshooting

- **Service exits with missing environment variables:** check that `MONGO_URI`, `DATABASE_URL`, `ADMIN_EMAIL` and `ADMIN_PASSWORD` are present in Render Environment. `JWT_SECRET` should be generated by the Blueprint.
- **PostgreSQL connection failure:** verify the Neon URL, password rotation, SSL query parameters and that the role has the required privileges.
- **MongoDB timeout:** check the Atlas database user, password URL-encoding and Network Access rules.
- **Initial seed hook fails:** review the hook logs, confirm both managed databases are reachable, and run the seed command once from a trusted environment with the same environment variables.
- **Health check fails:** inspect application logs. The app connects to both databases before listening, so it will not become healthy until both are reachable.

## Free-plan expectations

Free hosting is useful for a portfolio demo but not production reliability. Services may sleep when idle and have monthly quotas. Database-provider free tiers may have their own limits, expiry, storage caps or connection limits; review each provider's current terms before relying on the demo. Never store real public-service reports or sensitive personal data in this learning deployment.


## Continuous integration

GitHub Actions runs the algorithm/property suite and a separate API integration suite against disposable PostgreSQL 16 and MongoDB 7 service containers. The integration run seeds a throwaway database, starts Express on an ephemeral port, and checks auth/session, CSRF, pagination, report persistence, role guards, road updates, planner output and history. CI credentials and database services are disposable test values only; never copy them to Render.
